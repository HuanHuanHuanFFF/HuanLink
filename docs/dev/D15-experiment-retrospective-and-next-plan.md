## 3. 当前问题和主要难点

### 3.1 同步判断晚于压缩

**已确认事实：** `packages/core/src/delegation/context-manager.ts:78` 仅在事实游标未变时直接返回；有新事实时，104 行先调用 compact。`coordinator.ts:158` 再根据压缩输出的 change 决定是否同步。当前确实能跳过无关内容的发送，但不能因此省下该次压缩。

**影响：** 同一会话存在多个委派时，无关消息也可能触发多次模型调用；目前没有对调用次数、延迟或节省效果作系统测量。相关变化发送完整任务快照，尚无字段级增量协议。

**难点：** 任务相关性通常有语义，单纯比版本只能找出候选差异；如果每条消息先加一次模型判断，再压缩一次，成本可能更高。取消和缩权也不能被普通的“无关”分类误吞。

### 3.2 双方状态不对称，回执只证明有限事实

**已确认事实：** Core 保存本地快照、事实游标和 receivedRevision；Adapter 接受更新后调用 steer 并返回回执。初次派单的接收版本由 accepted 结果推得，后续同步才有显式控制回执。当前没有对端事实覆盖清单或可验证的“已经理解”状态。

**影响：** 主端不能只凭接收版本判断对方是否已按新限制行动，也无法自动区分“没有收到”和“收到但回应丢了”。观察到的任务进展也可能已过期。

**难点：** 应比较可观察事实，而非双方内部思考。需要区分收到上下文、执行器接受输入、实际操作结果，控制额外交流成本，并规定观测时间与版本。

证据：`packages/core/src/delegation/types.ts`；`coordinator.ts:103`；`apps/codex-a2a-adapter/src/delegation-execution.ts:157`。

### 3.3 权限暂停状态用错，增加了额外状态消费者

**已确认事实：** `codex-task-executor.ts:470` 把操作审批发布为 INPUT_REQUIRED；`delegation-task-store.ts` 为此额外挂载暂停后的事件消费者。Core 权限协调入口也只接受 input-required。A2A Client 在任一种暂停后结束观察。

10 月 4 日的对照说明，当前已安装的 `@a2a-js/sdk 1.0.0-beta.0` 就具备 AUTH_REQUIRED 后继续消费的能力。因此不能再把这层补丁归因为“SDK 没有授权恢复能力”。

**难点：** 必须同时迁移发布状态、Core 暂停门、控制快照、观察流和普通问答交叉序列。直接删除消费者可能丢结果；同时保留两个消费者又可能重复落库。这项纠正不依赖升级才可做，只是后续统一放在已明确的基线上验收。

证据：`coordinator.ts:127,193`；`a2a-agent-call-transport.ts:384,406,448`；[SDK beta 授权回归](https://github.com/a2aproject/a2a-js/blob/v1.0.0-beta.0/test/server/request_handler/auth_required.spec.ts)。

### 3.4 扩展声明与实际协商尚未闭合

**已确认事实：** Agent Card 声明 D15 扩展；客户端未完整请求/确认激活。服务端 controlMessage 在默认 handler 前处理，仅接收 Message，没有接入 ServerCallContext。私有回执携带另一个任务快照，需与 GetTask 保持一致。

**影响：** 当前双端配套实验能交流，不等于独立 Agent 理解相同权限合同。更新 SDK 不会自动保护提前截获的控制路径。

**难点：** 需要明确版本、不支持时的行为、任务和调用范围、回执阶段、重复与不确定结果。Task 与控制 Message 的选择应按实际互操作验收，不把官方解释性指南直接当成新的核心 MUST。当前仍是本地单用户实验，不据此断言已经出现跨租户漏洞。

证据：`apps/codex-a2a-adapter/src/agent-card.ts:26`、`server.ts:26,73,117`；`packages/integrations/a2a-client/src/a2a-agent-call-transport.ts:250`。

### 3.5 引用正确不等于授权判断正确

**已确认事实：** 程序检查 owner 身份、引用 ID、时序和审批目标；Reviewer 对具体操作作语义判断。原始证据保留是必要条件，但不能证明模型正确理解命令效果或用户范围。

当前授权缩小检测还比较 allowed/denied 的 scope 字符串，并要求模型保持原标签。**待验证风险：** 同义改写可能导致误停，摘要遗漏也可能导致权限判断缺少材料。不能把提示词要求当成稳定的权限类型系统。

**难点：** “可以”“继续”必须绑定当时唯一的问题；命令 cwd 在项目内也不意味着命令的全部效果被限制在项目内。不得用摘要、模型置信度或 SDK 的批准 API 代替原操作的授权证据。

证据：`context-manager.ts:185`；`coordinator.ts:350`；`delegation-execution.ts:90` 附近的命令/文件审批条件。

### 3.6 上下文维护的并发和预算仍需验证

**已确认事实：** 压缩期间事实游标变化会使本次结果失败；同步结果不明进入 uncertain 并阻止继续批准。预算按字符计，默认输入 48000、任务包 16000、最多 16 批；它不是包含全部提示词开销的精确 token 上限。来源窗口若已经用摘要替代原记录，当前构建器拒绝处理。

**难点：** 连续消息可能反复使摘要过期，需要合并触发或任务级串行化，又不能延迟取消。原话证据要能独立检索；授权确认即使与旧消息正文相同，也不能按内容 hash 丢弃。模型超时、证据预算不足与真正权限疑义应分开处理，避免技术故障变成重复询问用户。

### 3.7 持久化与执行恢复尚未连接

**已确认事实：** Core SQLite 保存事实和委派快照；Adapter TaskStore、pending approval、consumed 回执等仍在内存。先记录消费再向原生 RPC 写决定，可以限制部分重放，但有失败窗口；进程重启后不能据此重建有效审批。

**难点：** 一次授权可能已执行但回执丢失。保存 Task 不等于保存执行检查点，更不等于数据库、原生 RPC 与外部副作用的原子事务。结果未知时必须先对账，不能自动再次执行。

### 3.8 验证集中于受控流程，真实场景数据不足

目前缺少真实 QQ 到真实 Codex 的编码/原生审批闭环，以及长对话、多委派、矛盾授权、并发新消息的成组评估。早期真实模型曾引用非 owner 消息 ID，已被程序拒绝并改进提示；这说明程序校验有价值，也说明结构化输出成功不是语义正确证据。

## 4. 已修复的问题继续作为回归基线

以下是第一轮修过的问题，不应在复盘里重新列成当前未修复缺陷：

- 失配、关闭或孤立的原生审批要明确 deny；写拒绝失败则关闭执行端，不能只删除本地记录。
- 多任务裸确认、正文目标与回复引用冲突保持等待；A 的确认不能被 B 接着消费。
- 普通问题待答期间同步必须保留原问题 ID，并续接同一个 Task/turn；问题与权限请求异常并发不能互相覆盖。
- 前面分批压缩中的重要变更不能被后面的无关批次抹掉；同版本不同内容、旧版本和旧游标拒绝。

这些约束在状态迁移、SDK 升级和上下文优化后都要再次验证。历史通过记录不自动延续到新组合。

候选目标沿用 2026-10-05 已核对的正式发布：A2A JS 1.3.0；OpenAI Agents 与 agents-extensions 同步到 0.18.0。升级分支目前仍锁定 A2A beta、Agents 0.12.0，不能把下表写成已落地能力。

| 能力 | 对实验的计划用途 | 采用边界 |
| --- | --- | --- |
| A2A 原生 AUTH_REQUIRED 消费路径 | 迁移权限状态后，用原生机制替换额外 drain 做对照 | 当前 beta 已有，不计为升级新增收益；通过完整恢复回归再删除补丁 |
| A2A 扩展协商及新增终态/metadata 修复 | 明确激活 D15 协议，改善任务终态和可查询回执的一致性 | 控制旁路要显式接入校验；metadata 保存需实测 |
| A2A DatabaseTaskStore | 可选地先实现 Adapter 重启后查询历史 Task | 有数据库驱动与迁移成本，不自动恢复 Codex turn 或 approval RPC |
| Agents AI SDK 适配层文本和顺序修复 | 确认摘要、Reviewer 结构化结果、主 Agent 输出没有丢段或错序 | 用 DeepSeek 实际路径和合成多段输出回归，不能只看版本 |

| Agents 单次模型调用超时、取消和并行失败收尾改进 | 将单次推理期限与整个任务期限分开，检查取消后不再新派单 | 超时依赖提供方响应取消；已受理或效果未知的操作不自动重试 |
| Agents 自身的审批与可恢复运行状态 | 可研究本地 Tool 暂停恢复的接入点 | 不直接替代 A2A 远端授权、Codex 原生 RPC 或 Core 会话存储；没有本地需求前不重构 |

## 6. 升级后的候选实验批次

这些编号接续第一轮 B01 至 B04，均未启动。先完成各批的证据和失败处理，再进入下一批；不预设整批实验必须采用。

### B05 承接升级基线并建立对照

- **目标：** 分清 SDK 变化、最新运行时修复和实验变化各自的影响。
- **前提：** 统一升级分支分别完成 A2A、Agents/扩展的验收，记录实际依赖和提交；按批准的集成路径形成可用基线。原实验未提交，保留工作树和可核验快照，不对它强制重置或直接覆盖最新 Core/Server。
- **动作：** 原实验分支不会合并进 main。后续决定采纳的能力，从含已验收 SDK 升级的最新集成基线按正式功能批次重新实现或选择性移植，并逐项验证；不把原实验整支合入集成分支。先复现选定能力的受控闭环，再改变状态或同步算法。旧工作区仅作对照，SDK 升级批次也不因携带本文而自动扩大为全部实验功能。
- **检查：** 编译、类型、受影响包测试；DeepSeek 文本、工具、结构化结果、strict、超时/取消；最近集成分支的任务身份、持久化失败和入站串行处理回归。
- **退出条件：** 原受控流程失败先定位迁移层，不同时调整提示词和算法掩盖问题。没有升级验收证据，不宣称已有新版实验基线。

### B06 纠正权限状态并减少补丁

- **目标：** 权限暂停和普通输入暂停各自采用正确生命周期。
- **改动位置：** Adapter 权限发布与回执、Core resolvePermission 入口、A2A Client watcher 和错误映射。
- **检查：** 自动批准、一次询问、明确拒绝、过期/取消；AUTH_REQUIRED 后继续产出；授权恢复后又遇普通问题；普通问题期间同步；回执丢失后 GetTask 对账；每个结果只落库一次。
- **采用条件：** 在额外 drain 开启/关闭两组中验证同一套行为。全部通过再移除 `DelegationTaskStore` 的附加消费逻辑，不能只换枚举。
- **退出条件：** 丢失 Task/turn、原问题、Artifact、终态，或出现双写时保留补丁并定位。该批技术上可在旧 SDK 独立预验证，不必因为升级延期而误认为无法研究。

### B07 补齐扩展合同和可对账回执

- **目标：** 双方明确使用同一版本的上下文/授权协议；传输未知有确定处理方式。
- **动作：** 补齐声明、请求激活、服务端检查、激活响应；校验 Task/Context/Delegation、revision、approvalId 与调用范围；保留既有原操作绑定。
- **默认方案：** 当前本地实验先保留明确激活的 Message 控制回执，GetTask 是任务状态查询入口。对外通用客户端确有需求时，再验证 Task metadata 回执方案；不顺带创建新 RPC 或统一权限平台。
- **检查：** 未激活/版本不符/一侧关闭/错任务均在效果发生前拒绝；正常任务无需启用 D15；重复决定不再执行；丢回执可查，未知状态不会自动放行。官方 TCK/ITK 可补互操作检查，私有合同仍需专属用例。
- **退出条件：** 回执与 GetTask 分叉、绕过协商执行、相同 approvalId 接受不同操作，均停止推广。

### B08 先判断信息差再准备上下文

- **目标：** 减少无关压缩和重复发送，保留任务必需信息及新授权证据。
- **输入：** 新增事实和 owner 原话；上次发送/接收版本；远端可观察阶段、产物引用、待答问题及观测时间。只在阶段变化或受阻时请求必要反馈，不让双方持续交换全部历史。
- **决策：** 明确取消或限制变化优先处理；然后以事实 ID、任务归属和版本筛掉确定重复；语义不清时做有限判断或保守准备。需要同步的短内容直接发送，长材料再压缩；状态不足时定向询问远端，不能由模型编造对端已知事实。
- **保留条件：** 同正文的新确认保留独立 messageId、owner、时间和审批目标。预算不足、模型故障和真实授权疑义分别记录；技术故障先安全重试只读分析或报告不可用，不自动反复要求用户授权。初次委派按任务建立最小基线，不强行增加一次信息差推理。
- **检查：** 在相同人工标注样本、相同模型配置和输入预算下比较旧策略与候选策略。规则明确场景应省去压缩调用；语义场景以关键约束覆盖为先，不固定每条消息两次模型调用。
- **退出条件：** 取消/缩权/新禁令被遗漏、跨任务误确认、成本增加却无质量收益时不采用优化；保留能定位到原话、版本和判断依据的记录。

### B09 真实闭环及最少打扰验证

- **目标：** 把受控协议正确与实际任务效果、语义判断质量分开验证。
- **步骤：** 先合成数据的真实模型评估，再在独立测试项目跑真实 Codex，最后验证 QQ 入站、确认指向和结果回流；使用独立配置与数据，不覆盖用户原服务。
- **检查：** 至少覆盖明确已有授权、明确禁止、任务范围变化、多委派歧义、普通问题与权限交叉、连续新消息、取消、长材料与丢回执。真实命令和补丁须有可观察结果，不能只统计接口成功。
- **采用条件：** 每类报告样本数、关键错误、额外询问与重复询问、时延和模型调用量；阻断性的错误先修复。小样本无错误只说明该组用例通过。
- **退出条件：** 任一明确禁止操作被批准，或缺少有效证据仍执行，停止自动批准实验；不可观测的结果保持未知，不以摘要声称成功。

### B10 可选的任务历史持久化

完成前面批次后，按真实需要试用 DatabaseTaskStore。第一阶段仅验收重启后可查询旧 Task 和产物；活跃任务标记需对账，旧审批不自动批准。只有原生 RPC/turn 续接、资源占用、持久化消费记录和重放行为都有独立证据，才讨论执行恢复。没有必要先引入分布式锁、共享记忆或完整凭证生态。

## 7. 评估记录和交付要求

| 指标 | 记录方式 |
| --- | --- |
| 关键约束遗漏 | 按样本标注必须保留的限制，对照实际发送内容和具体操作；取消/缩权单列 |
| 错误放行 | 按具体原生操作计数，保留授权原话和决定依据；分母是本次有判定的操作 |
| 用户打扰 | 区分必要澄清、重复询问和模型/系统故障造成的询问；按可比较任务组统计 |
| 同步效率 | 每个任务的判断/压缩调用次数、发送次数、字符量或实际 usage；没有 token 数据时不估成精确 token |
| 可靠性 | 回执丢失、重复、乱序、过期和重启分别统计；区分收到、接受输入和实际效果 |
| 成本和时延 | 单次模型、端到端任务分别报告；样本足够时才报告有意义的分布 |

每批交付应包含实际改动范围、基线 SHA 与依赖版本、保留/删除的补丁、通过与失败样本、仍未知的事项和下一停止点。测试适用范围以受影响包和根脚本为准；文档整理本身不触发全量运行测试。第一轮的 917/2 不能写成后续批次的新结果。

本文刻意保留的未知项是授权语义正确率、信息差判断质量、实际用户打扰频率与执行恢复能力。SDK 提供可靠机制的机会，是否适合当前实验必须由上述可观察结果决定。
